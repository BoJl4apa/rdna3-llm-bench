# 2026-10: Ollama 0.35.0 on ROCm, and two typed-judge engines

**TL;DR** — Moving from Ollama `0.33.2-rocm` to `0.35.0-rocm` broke nothing.
Every route that worked before works after. Decode moved −9 % to +19 % on
single samples. The two largest models failed to load on **both** versions,
and the cause is host memory, not the engine. 0.35 also adds **System One**
(`POST /v1/systemone`). It answers typed questions with probabilities, not
text, and on gfx1100 it runs fully on the GPU with sub-0.3 s warm answers.
Separately, the **CLM-v0.1-8B** contrastive verifier serves on vLLM 0.19.1's
ROCm pooling runner at a 32k context. Stock `clm-serve` silently truncates
input at 2,048 tokens, though.

## Ollama 0.33.2 → 0.35.0 route smoke

This is one generation per model ("Write four sentences about rivers.",
`num_predict` 200, temperature 0, seed 1), on the same box on the same day,
with the model unloaded between runs. Rates come from Ollama's
`eval_count`/`eval_duration`. **These are single samples:** read a ±10 %
move as noise.

- **The two pool models failed on both versions.** mistral-small-4 119B and
  gpt-oss 120B are the two largest models, layer-split across both cards. Neither came up within Ollama's 5-minute load
  timeout, and the engine logged a timeout waiting for the runner to start.
  At the time, two virtual machines on the host held about 33 GB of its RAM.
  Both models loaded and benched on earlier engine versions (see the
  [2026-08 round](2026-08-unified-final.md)), and they fail identically on
  0.33.2 and 0.35.0. So this is a host-memory finding, not an engine
  regression.
- **The qwen3.8 MTP row is the only move over 15 %.** Its 28–34 tok/s on this
  short prose prompt is not comparable to the 42.1 tok/s median in the
  [Qwen3.8 MTP page](2026-09-qwen3.8.md). That figure is the median over 100
  coding completions, and MTP's gain depends on how predictable the text is.
- Several generations stopped before the 200-token cap: 70 to 163 tokens on
  seven of the models. Run lengths differ slightly between versions, which
  makes the small deltas noisier still.

## System One: typed questions on Ollama 0.35 (ROCm)

`POST /v1/systemone` takes a `state` (free text) and named `questions`, each
typed as one of the following:

- `choice`: pick one key from `criteria`;
- `noul`: a probability that the answer is yes;
- `score`: a point on an ordinal scale that `criteria` lists.

It returns a probability distribution per question, never generated text.
The request and response follow the wire schema of TypeSafe's hosted **Jev**
API, so a request written for that API replays against a local model with
only the URL and the model name changed. It serves only the System One model
families. An embedding model returns 400 ("not supported by System One"),
and an unknown tag returns 404.

All three models ran on gfx1100. Each request asked one question of each
type about a one-line commit message:

| model | placement (`size == size_vram`) | VRAM | cold request | warm request | `num_ctx` |
|---|---|---:|---:|---:|---:|
| nimble:9b | 100 % GPU | 8.2 GiB | 2.86 s | **0.27 s** | 8,194 |
| tev1:4b | 100 % GPU | 4.3 GiB | 2.02 s | **0.24 s** | 2,050 |
| tev1:0.8b | 100 % GPU | 0.8 GiB | 1.18 s | **0.09 s** | 2,050 |

The answers, to show the shape rather than the quality, from one state and
one sample:

| model | `kind` = bugfix | `breaking` (noul) | `clarity` score, 0–3 |
|---|---:|---:|---:|
| nimble:9b | 0.968 | 0.015 | 2.23 |
| tev1:4b | 0.978 | 0.118 | 1.88 |
| tev1:0.8b | 0.758 | 0.464 | 1.27 |

Two behaviours matter more than the speed:

- **Over-length input returns 400 and is never truncated.** The error is
  `prompt 0 has 11218 tokens; expected 1–2050 (input is never truncated)`.
  That is the safe failure for a judge, because a truncated state would be
  scored silently.
- **`num_ctx` bounds the whole prompt, not just the state.** The questions
  count against it. 64 one-line yes/no questions about a 2-character state
  came to 2,552 tokens and overflowed tev1's 2,050. A wide question set eats
  the room you thought you had for the state.

## CLM-v0.1-8B on vLLM's ROCm pooling runner

[CLM-v0.1-8B](https://huggingface.co/Contrastive-LM/CLM-v0.1-8B) is a
contrastive verifier: two small projection heads on a **frozen Qwen3-8B**
encoder. It scores typed questions or candidate lists against a state, much
like System One. It runs as two processes. vLLM serves Qwen3-8B
last-token-pooled embeddings, and the
[`contrastive-lm`](https://github.com/Contrastive-LM/CLM) 0.1.0 package's
`clm-serve` applies the heads on CPU.

- **It works on gfx1100.** We ran `vllm serve Qwen/Qwen3-8B --runner pooling
  --max-model-len 32768 --gpu-memory-utilization 0.5` on the
  `rocm/vllm` 0.19.1 / ROCm 7.13 gfx110X image, on one card. That gives
  15.34 GiB of weights plus a 5.57 GiB KV cache (40,560 tokens), and the card
  goes from 0.39 GB to **22.5 GB** used. Cold start to serving takes about
  60–72 s.
- **Latency:** 0.25–0.42 s for a state of ~1.4–1.6k tokens, and about
  21.5–23 s for a ~25,000-word state.
- **Stock `clm-serve` truncates silently at 2,048 tokens.** Its
  `--max-tokens` (env `CLM_EMB_MAX_TOKENS`) defaults to 2048 and is sent to
  vLLM as `truncate_prompt_tokens`. A long state is cut, embedded and scored
  with no signal that anything was dropped. The model card's own recipe also
  pins `--max-model-len 2048`. We run `--max-tokens 0`, so no truncation is
  requested, together with a small wrapper. When vLLM rejects a prompt over
  `max-model-len`, the wrapper turns that into **HTTP 422 with the reason**. A ~40k-token state now returns 422.
- **Quality beyond 2k tokens is unvalidated.** We raised the context to make
  long states *possible*. We have not measured whether the heads still rank
  well on them.

## Threats to validity

- **n=1 per cell** throughout: one generation per model in the smoke, one
  state per System One model, and a handful of CLM timings. Nothing here
  measures variance.
- **The pool-model failure was not rerun with the VMs stopped.** The
  host-memory attribution comes from the conditions (identical failure on
  both versions, earlier successful loads, ~33 GB held by VMs), not from a
  controlled A/B.
- **System One answer values** are shown to illustrate the output shape. We
  have not measured these judges' accuracy.
- The CLM numbers come from one card, one image and one engine flag set. The
  long-state latency should track the 8B encoder's prefill rate.
